01The approach

Every round in this project followed the same rule, stated by the client early on and kept for the rest of the work: add, don't replace.

Rather than converging on one "final" landing page, each request produced a new, independent variant — different visual language, different information architecture, sometimes a different buyer journey entirely — while anything already shipped stayed exactly as it was. Concretely, that meant:

  • New sections use their own CSS class prefixes and element ids, so a new stylesheet block or script IIFE can never leak into, override, or race against an existing one.
  • Every addition was verified in a real browser (Playwright) against both the new content and the sections around it, specifically checking that nothing upstream or downstream had changed.
  • The client always keeps a full set of options on disk and can say "remove this one" later — nothing was designed to be a dead end.

The payoff: seven pages now exist side by side, each a legitimate answer to "what should base360.ai look like," and the client can compare them directly instead of trusting a single opinion.

02Principles applied

Six patterns show up repeatedly across the variants. Each one exists because a specific problem showed up during review.

User-controlled pacing over autoplay reading experience

The first hero story auto-advanced every 4.2 seconds. It looked good, but it forced everyone to read at the same speed — too slow for a skim, too fast for someone actually reading the detail line.

Applied in: index.html#how-scroll replaces the timer entirely with an IntersectionObserver keyed to scroll position — the phone mockup only advances when the reader's own scroll crosses into the next step. Nobody can get ahead of it or fall behind it, because it has no clock. The original autoplay version was kept, unmodified, as #how for comparison.

Show, don't tell conversion

A static "AI replied · 4s" badge is a claim. Letting someone click a channel and watch a message actually get answered is evidence. The gap between those two is most of what separates a landing page people skim from one they trust.

Applied in: the #unify section (multi-channel demo) and the hero live-demo in alt-tryit.html — both are real DOM state machines (typing indicator → reply → "filed to CRM"), not looping videos or CSS-only animation. aria-live="polite" regions mean the same evidence reaches screen reader users, not just sighted ones.

Quantified contrast beats a features list conversion

"AI agents, every channel" is a feature. "10 messages in, and the human column still has 4 that were never answered" is a consequence. The second one is what actually gets remembered.

Applied in: the #race section — a human-team-vs-Base360 simulation run on identical input, ending in a scoreboard (avg reply time, comments never answered). It's deliberately not framed as 100% AI vs 0% human effort; the copy is honest that it's comparing against "duct-taped tools," which is the actual competitor.

Different buyers need different pages, not different paragraphs information architecture

A visitor ready to sign up today and a visitor who needs to loop in three teammates before deciding are not served by the same page with an extra FAQ bullet. They need different primary actions.

Applied in: alt-tryit.html ("Try It Now") leads with a single low-friction CTA and an instant demo. alt-walkthrough.html instead offers three calibrated actions — book a walkthrough, start free, or copy a link to send a teammate — plus a live ROI calculator, because that reader's blocker isn't curiosity, it's needing to justify the decision internally.

Numbers you can act on, not just numbers you can read wow / trust

A number that never changes reads as decoration. A number that visibly responds to what you just did reads as proof the system is real.

Applied in: the ROI calculator in alt-walkthrough.html recomputes live from a slider input. The #race scoreboard in index.html was reworked (see the change log below) from a single reveal-at-the-end panel into four stats that count up in real time as each simulated reply resolves.

Motion is a tool, not a default accessibility

Every animated section — the demo flights, the race, both story formats — has an explicit prefers-reduced-motion path that renders the finished end-state instantly instead of skipping the content or leaving it half-built.

Applied throughout: interactive controls use real semantics (aria-expanded on the FAQ accordions, aria-pressed on toggles, aria-live on regions that update on their own), and every custom control is keyboard-operable, not just clickable.

03Review → change log

A specific example of the "add, don't replace" workflow in practice — three pieces of direct feedback on index.html, and exactly what changed in response.

1 · The "answered here" stats felt like decoration, not proof

Before

Three bare numbers — 18 / 9s / 6 — with labels but no baseline. Correct information, but nothing to measure it against.

After

Each stat now carries a comparison line: vs. 0 replied manually, vs. ~4 hrs typical first reply, vs. 6 separate logins.

Why: a number only means something in contrast to an alternative. Pairing each stat with what "without Base360" looks like turns three facts into an argument.

2 · The autoplay step list was hard to read mid-transition

Before

Steps switched every 4.2s. The detail line under the active step used display: none → block — an instant, layout-shifting pop that competed with the reader's eye.

After

Interval shortened to 3.4s; the detail line now animates in on opacity + max-height over 0.32s with a slight delay, so it eases in instead of jumping.

Why: the request wasn't "slow it down," it was "stop interrupting me." A faster cycle with a softer transition reads calmer than a slower one with a hard cut.

3 · The race scoreboard only appeared after the full animation finished

Before

Four summary stats (avg reply time, comments never answered) were hardcoded strings, hidden until a setTimeout fired at the very end of a ~6.5s sequence.

After

The panel is visible from the moment the section loads, showing — placeholders, then computing real running averages from each reply as it resolves — with a short highlight pulse on every update.

Why: a summary you might miss isn't a summary. Making it live removed the "did I miss it?" risk and turned a static reveal into another piece of visible proof.
